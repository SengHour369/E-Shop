## Delivered behavior

The fixed `ImportTool` registry is shared by staging and catalog-service. It declares schemas, function grants, risks, confirmation and fixed handlers. Spreadsheet content cannot register handlers or select arbitrary URLs. Category, SKU, stock-in, stock adjustment and draft-percentage-promotion imports use catalog-owned services. Branch and spreadsheet-only Product imports remain explicitly disabled for the repository constraints above. There are no cross-service database writes.

All eleven requested staging tables are represented by JPA models and a PostgreSQL upgrade script. The original file bytes and SHA-256 checksum, original cells, proposed and confirmed column mappings, current edited values, deterministic errors, optional AI explanations, immutable validated snapshots, approval decisions, execution attempts and audit history are retained. Reports contain original/current values, validation and execution errors, statuses and confirmed resource IDs. Reports escape CSV formula prefixes.

XLSX worksheet XML is streamed; XLS uses the bounded legacy POI reader. The parser checks actual content, rejects formulas, encryption, VBA, macro-enabled OOXML, embedded objects and external-link workbooks, checks ZIP entry counts and expanded sizes, caps expanded cell text at ten million characters and limits concurrent parsing to two requests. Inference receives only headers or registered error codes, never workbook rows. AI output remains advisory; every sheet mapping requires explicit confirmation and all validation uses backend rules and authoritative catalog APIs.

Each mutation requires the current batch `version` (the returned `revision`), locks the batch and invalidates earlier validation/approval. Every approval requires an independent assigned reviewer, including low-risk imports. The uploader and the last editor cannot approve their own work. Reviewer edits require the uploader to resubmit to another independent reviewer. Staff pending queues contain only their assigned submitted batches; administrators can browse all submitted batches.

Approval and execution are separate explicit actions. Execution is performed by the approving reviewer with fresh review, approval, execution and domain grants. Calls process at most ten rows; call `execute` again while status is `PROCESSING`. Pending rows precede retries of failed rows. Once execution begins, the batch cannot be edited. A failed domain response is recorded as unconfirmed, with no invented resource ID. Retry uses the same batch/row idempotency key. Catalog verifies a short-lived HMAC approval proof bound to the actor, revision, key and exact payload, then revalidates the data. Its receipt and business mutation commit in the same PostgreSQL transaction; natural-key advisory locks and inventory row locks protect concurrent imports. Replaying a successful receipt returns its confirmed resource ID without repeating the operation.

Import lifecycle notifications reuse the existing transactional outbox, Kafka topic and deduplicating consumer. Notifications go to the uploader and assigned reviewer. Producer retry tests and consumer redelivery tests exercise the reused delivery paths; a live Kafka cluster integration test was not performed.

## Deployment and permissions

Apply each `20261013` upgrade script to its owning database using the project's existing upgrade process:

- ai-service: `20261013_ai_excel_import.sql`
- catalog-service: `20261013_ai_import_receipts.sql`
- auth-service: `20261013_ai_excel_import_permissions.sql`
- notification-service: `20261013_import_notifications.sql`

Set the same private `AI_IMPORT_SIGNING_KEY` (at least 32 characters) for ai-service and catalog-service. Compose passes it through; `.env.example` deliberately has no default secret. Domain execution fails closed without it. Apply migrations before deployments that use `DDL_AUTO=validate`.

ADMIN and SUPER_ADMIN accounts automatically receive all active, nondeleted function definitions through the live authorization service. Assign staff grants through the existing permission administration APIs. Uploaders need `IMPORT_UPLOAD` plus each imported domain's permission. Reviewers need `IMPORT_REVIEW`, `IMPORT_APPROVE`, `IMPORT_EXECUTE`, plus the same domain permissions. Administrators can browse all batches and all submitted review batches, while staff lists retain owner/assigned-reviewer scope. Approval still requires the assigned independent reviewer. The registry provides the exact permission for each tool. Existing promotion services additionally require the project's administrator role. SKU codes come from the existing generator, initial SKU quantity must be zero, and inventory changes must be imported separately against an existing inventory ID. No branch or warehouse access is inferred from a spreadsheet; unknown branch fields/types fail closed. Branch-scoped imports cannot be enabled until authoritative branch authorization is available.

Default limits: 5 MiB upload, 6 MiB multipart request, 10,000 workbook data rows, 64 columns and 16 worksheets. `AI_IMPORT_MAX_BYTES`, `AI_IMPORT_MAX_REQUEST_BYTES`, `AI_IMPORT_MAX_ROWS`, `AI_IMPORT_MAX_COLUMNS` and `AI_IMPORT_MAX_SHEETS` configure these limits. Dates must be explicit ISO local timestamps; serial Excel dates are not inferred. Missing booleans or foreign keys require correction rather than guessing. Column mappings may explicitly ignore irrelevant columns.

## APIs and dashboard integration

Domain validation uses fixed `/internal/ai/imports/validate-bulk` calls of at most 500 rows, preserving one result per input row. Permissions are resolved once per distinct tool per domain request; the AI service resolves its live grants once per validation operation. Duplicate detection still spans all chunks and worksheets. This avoids per-row authorization/network round trips while keeping domain rules authoritative.

The requested upload, analyze, preview, row edit, validate, submit, approve, reject, request-changes, executions and CSV report APIs live under `/api/ai/imports`. Additions are `GET /tools`, `GET /` (owned batches or `?review=true` pending assignments), `PATCH /{id}/sheets/{sheetId}` (confirm mappings), `PATCH /{id}/rows/{rowId}/skip`, `POST /{id}/execute`, `GET /{id}/history` and `GET /{id}/original`. Mutation bodies require `version`; submit additionally takes `reviewerId`, review decisions take `reason`, row edits take `values`, and mapping confirmation takes a registry `tool` and a header-to-field `columns` object. All downloads require the same access checks as preview.

Preview includes `summary: {totalRows, editedRows, statuses}` aggregated in the owning database across the entire batch. Counts are independent of the current row page/filter; edited rows are an overlapping count, not a separate execution status. The preview access check runs before summary queries. This avoids loading every workbook row merely to calculate dashboard totals.

`GET /api/ai/imports?assigned=true` requires `IMPORT_REVIEW` and lists the caller's assignments across all statuses. `review=true` continues to list only pending submissions. Administrators retain their existing all-batch visibility. This gives staff reviewers access to approved/completed execution history without requiring upload grants or broadening access to other users' batches.

The existing gateway already routes `/api/ai/**`. The new standalone Angular import component is embedded in the existing chat example when `importPermissions` contains `IMPORT_UPLOAD`. Supply live permission codes from the host application's access response. Mount `<app-ai-import [permissions]="permissions" [reviewer]="true">` on the approvals page. For an execution/detail route, pass `[initialBatchId]="batchId"`. It supports paginated row previews, validation/duplicate/edited/created/failed/skipped filters, mapping confirmation, correction, skip/include, review decisions, original downloads, reports and audit/execution history. It uses the host authentication interceptor and escaped text bindings.

Uploads in the chatbot are visible to staff and administrators holding `IMPORT_UPLOAD`. Batch and row lists have separate page controls. The summary displays whole-workbook status counts, while the table indicates the filtered count. Mapping suggestions remain visible after confirmation. Correction inputs include every registered field, including fields absent from a row. Preview loading blocks writes, and stale preview responses cannot replace a later selection.

The actual Angular dashboard repository is absent, so its routes, navigation and application build remain external integration work. Product image workflows and the Branch service/access contract are also required before enabling those import types. The implementation is not a claim that every item in the original production rollout specification is complete. Local runtime deployment additionally requires matching catalog/notification images, their database migrations and the shared import signing key; source verification alone does not establish those deployment prerequisites.
